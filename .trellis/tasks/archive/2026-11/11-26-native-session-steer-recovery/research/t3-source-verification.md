# Research: T3 Code 的 Codex Steer、Stop 与恢复

- Query: T3 Code 怎样反馈忙碌会话的追加消息、区分送达回执、解除 Stop 和尚未确认送达的 Steer。
- Scope: mixed
- Date: 2026-11-26

## Findings

- 核对的是 T3 Code `main` 的固定提交 `6ac4edef8cd02ec655b999d213f18e149171a867`。产品文档给出 Queue 和 Steer 两种行为。排队消息可立即派发、编辑和移除。Stop 或服务器重启后保存原队列顺序，空输入框可以 Resume。 [Composer](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/docs/user/composer.md#L33-L55) · [Queued messages](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/docs/user/composer.md#L117-L125)
- `Orchestrator.ts` 先提交应用事件、命令回执和后台待办，客户端接收的序列只证明这次应用提交。后台启动时从已保存的消息读取原 ID 和正文，Codex 适配器再用当前原生轮次的 `expectedTurnId` 调用 `turn/steer`，等待 JSON-RPC 响应。这个响应证明 Codex RPC 成功返回。是否采用输入仍取决于后续 provider 事件。投影有单独根据 `steer.updated` 更新用户项状态的路径。原生 `turn/start` 的代码也明确区分了 RPC 回复、`turn/started` 和实际记录的 `userMessage`。 [应用命令提交](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Orchestrator.ts#L16729-L16749) · [应用回执序列](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Orchestrator.ts#L16823-L16827) · [已存消息送入适配器](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/ProviderTurnControlService.ts#L440-L485) · [Codex Steer](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L8717-L8789) · [Steer 投影事件](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/ProviderEventIngestor.ts#L655-L682) · [Codex 启动确认](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L8123-L8151) · [实际记录用户消息](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L7846-L7863)
- `turn/start` 在该提交上已有两分钟 RPC deadline。到期主动将 Codex app-server 标为失去响应，退役共享 runtime，并将该 RPC 失败交还给调用者。源码明确认为未回复的请求执行结果未知，deadline 本身不把该 RPC 当作一次未送达来自动重发。另有测试等待一个已写出、没有响应的 `turn/start` 并断言 deadline。 [固定时限](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L623-L635) · [deadline 和会话退役](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L2286-L2314) · [启动调用](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L8123-L8130) · [测试](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.test.ts#L1611-L1697)
- Codex `turn/steer` 没有套用该 deadline。适配器、会话管理层都没有找到针对这一 RPC 的时限，通用解析层会在请求入队后等对应响应。后台 worker 的 30 秒只释放 worker 槽位，该会话仍持有运行中的 effect，直到完成、取消或恢复。明确的轮次已结束或 Steer 被拒绝才进入即时转派分支，复用原消息 ID，由确定的命令 ID 防止创建重复后续消息。 [Steer 和 Stop 包装](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/ProviderSessionManager.ts#L2766-L2790) · [RPC 响应等待](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/packages/effect-codex-app-server/src/protocol.ts#L538-L568) · [同会话 effect](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/EffectWorker.ts#L737-L758) · [释放槽位](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/EffectWorker.ts#L1059-L1098) · [明确拒绝后的转派](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/EffectWorker.ts#L333-L413)
- Stop 暂停排队消息。Stop 的 provider adapter 调用受外层 15 秒时限约束，内层 Codex 在 `turn/interrupt` 回复以后尝试等最多 10 秒的原生结束事件，受外层总限约束。未确认就保留活跃轮次，记录无响应，供用户 Force stop。Force stop 会用目标 run ID 防止误停后续轮次，在锁内检查并终止独立运行环境。共享进程仍被其他会话使用时会分离当前会话，前端可显示仍在关闭或共享进程继续运行。 [Stop 暂停队列](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Orchestrator.ts#L14704-L14720) · [15 秒时限](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/ProviderSessionManager.ts#L83-L88) · [10 秒时限](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L173-L177) · [Codex 结束确认](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L9173-L9278) · [未确认状态](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/EffectWorker.ts#L279-L304) · [Force stop 服务](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/ThreadManagementService.ts#L1450-L1521) · [共享和延迟关闭](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/ThreadManagementService.ts#L1526-L1610) · [Force stop 界面](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/web/src/components/chat/useForceStopThread.ts#L17-L61) · [未确认 Stop 测试](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.test.ts#L12432-L12464)
- 轮次结束或服务恢复时仍处于 pending 的 Steer 会进入补偿路径。没有显式 Stop 时，服务按原队列先后保留消息 ID 并重新排队。有过 Stop 时，服务会标记这条 Steer 为取消，在会话显示送达未确认，附原文供用户决定是否重发。进程丢失时会取消与该进程绑定的旧 effect，恢复逻辑保留 pending 用户项给上述补偿。 [Stop 后的未确认提示](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Orchestrator.ts#L3575-L3653) · [保序重新排队](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Orchestrator.ts#L3655-L3704) · [轮次终止入口](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Orchestrator.ts#L16993-L17006) · [重启恢复入口](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/Orchestrator.ts#L17252-L17270) · [保留待确认用户项](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts#L756-L772) · [清理旧 effect](https://github.com/pingdotgg/t3code/blob/6ac4edef8cd02ec655b999d213f18e149171a867/apps/server/src/orchestration-v2/EffectOutbox.ts#L553-L580)

## Caveats / Not Found

- 源码和回放用例经过查阅，桌面 UI 和测试未实际运行。未确认 Codex adapter 对普通根轮 Steer 有逐条、可实时显示的消费回显，通用 `steer.updated` 分支的存在不能证明这个 Codex 路径会发送该事件。
- 仍在运行的轮次与未响应的 Steer 可能卡在同会话后台 effect。上述重新排队依赖轮次结束或恢复事件，且“仍为 pending”只表示应用尚无读取记录，不能证明 provider 没有执行。
- PR #37992 截至核对时仍开放，只作为候选变更，不作为上述 `main` 行为的依据。 [T3 Code PR #37992](https://github.com/pingdotgg/t3code/pull/37992)
