# Windows 多会话无响应现场

用户在 2026-11-26 19:23 左右报告多个会话同时卡住。取证只读取进程状态、SQLite 元数据、Codex 事件类型和时间。安装版 Native 进程于 19:21:54 启动，当时另有一个独立的开发版窗口。

- 安装版 Native 同时有三个独立 Codex app-server 子进程。三个会话在 19:21:58 至 19:24:28 之间都有事件。一条会话 19:23:12 记下回合结束，19:24:28 又启动新一轮。
- 19:24 至 19:25 的 Windows 消息探测中，Native 窗口线程应答，SQLite WAL 持续更新。Windows Application 日志在查询的两小时内未查到相关崩溃或挂起报告。这些采样覆盖报障后的窗口，原始卡住瞬间的 UI 线程栈和操作记录仍缺失。
- 修复前的单会话路径可能一直等待 Codex 的中断回执，也可能拿到回执就过早收尾。这两种情况已经用假 app-server 重放。
- Windows 空闲进程池在过期清理和若干删除路径持锁回收进程。进程退出和管道线程收尾期间，其他会话不能取得共用锁。修复将失效池项在锁下移出，释放共享锁后再完成回收。该阻塞机制已通过并发测试验证，现场是否命中同一条路径仍待确认。

## Windows 回归

- 核心 provider 筛选通过 114 项。并发用例让第二个模拟代理预先就绪，在第一条会话等待 Stop 时直接观察另一条 Steer 的回执。该用例在套件通过后又单独通过两次。进程池用例在析构仍阻塞时验证共用锁可取得。
- Native 队列筛选通过 15 项。覆盖停止期间保留排队、明确失败保留原文，以及送达未确认的消息不会再次派发并仍能接受同一回合的迟到确认。
- 最终 Windows Native 源码通过 `cargo +1.98.1 ncheck -p monocode-gpui --bin monocode-gpui -j 2`，仍有基线编译警告。修复在本地工作树 `fix/native-session-steer-recovery`，安装版仍用原构建。
- 2026-11-27 将主线 #22 的代理状态更新与停止收尾合并，补测工作树创建失败时的未确认队列状态。最终 Windows 本地通过 118 项代理测试和 16 项队列测试，GitHub CI 通过。修复已合入 `main`，提交为 `7106f9c1`。[PR #25](https://github.com/Yiiu/monoptah/pull/25) · [CI](https://github.com/Yiiu/monoptah/actions/runs/45924180467)
- 待验收场景是同一 Windows 安装版的真实窗口再次出现多会话整体无响应时，记录用户输入是否到达应用队列、UI 是否继续消费 provider 更新、是否正在回收进程。旧回合退出后才到达的回执继续按未确认处理。若在首个派发后、未确认状态写入前强制结束应用，重开会暂停恢复的队列，界面可能没有保存该次派发的状态。
