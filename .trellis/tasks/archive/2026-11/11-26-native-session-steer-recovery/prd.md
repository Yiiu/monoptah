# 修复 Native 会话追问卡住与停止后无法恢复

## 目标

一个会话长时间显示生成中时，用户能知道追问是否发出、是否被代理接收，以及还能做什么。需要停止时，可以恢复当前会话的发送能力，保留已有回复和待发消息，无需重启整个 Monoptah。

## 现场证据

- 2026-11-26 Windows Native 本地 Codex 会话的一轮在 17:47 开始，持续轮询 GitHub Actions。约 18:31 Monoptah 的暂停队列留有一条消息。点 Steer 后，保存记录里的 `steer` 为 `true`，当前轮的 Codex 记录未出现该条用户输入。
- 上一轮在 18:40:56 结束。Monoptah 随即清空队列，18:41:09 Codex 在新一轮记录了同一条消息。Monoptah 没有重启。
- 现场确认了消息没有在当前轮送达。尚缺按钮到 provider 写入的逐段事件，因此还无法区分本地派发条件未满足与 Codex 未回确认。代码中确认了 Codex Steer 与 Stop 都有可能无期限等待回复。
- 用户也在 Claude 会话遇到过长期显示生成中。主线已有 Claude 后台任务的显示和状态处理，复现时需要保留现有行为。
- 约 19:23 用户报告多个会话同时无法操作。事后采样确认应用消息循环应答、多个 Codex 会话仍有新事件。把跨会话响应性纳入同一 Windows 回归。[现场记录](research/2026-11-26-multi-session-stall.md)

## 范围与验收

范围为本地 Native 普通会话，首个现场和主要验收平台为 Windows。覆盖 Codex 的 Steer 和 Stop，以及 Claude 对共享队列和会话恢复路径的回归。Reclaude 启动早退后保存错误 ID 另有补丁。

| 编号 | 用户可观察行为 | 验收 |
| --- | --- | --- |
| R1 | 点击 Steer 后马上看到消息当前的发送状态。客户端暂不能发送、已发出等待确认、代理已接收、发送失败和接收结果未知都能区分。 | 重现忙碌会话和暂停队列，分别模拟派发受阻、成功确认、拒绝和迟迟未确认。每种情况都有反馈，正常的长工具调用可继续运行。 |
| R2 | 发送结果未知时原消息仍可见，并能在接收结果明确后继续处理。 | 模拟迟到确认、确认丢失和回合结束。已接收的消息只入历史一次，尚未确认的消息不会自动重发，明确拒绝的消息可以手动重试。 |
| R3 | 用户点停止后，在有限时间内看到当前轮已结束或看到明确的恢复状态。用户能够在同一会话继续发送。 | 分别模拟正常停止、无确认且进程仍在线、已确认但未收到终态、停止时收到迟到的结束事件。验证上一轮与下一轮隔离、队列及附件保留、其他会话继续运行。 |
| R4 | 复现时可定位请求卡在本地队列、传输、代理确认还是回合收尾。 | 本地日志可用不含正文和凭据的事件串起这四段。用 Windows 构建重放本次路径，验证解除阻塞无需重启应用。 |

## 本次规划选择

优先复用现有消息队列和停止入口。继续等待或停止当前轮由用户决定。对于尚未明确接收结果的请求，先保存消息并给出状态，待结果明确再决定是否发送。具体等待阈值依据 Windows 复现和 provider 测试确定，验收须覆盖其上限。
