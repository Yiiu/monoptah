# Native 对话保存：降低写入量与避免界面等锁

日期：2026-11-16。状态：规划提案，尚未实施。代码基线：`d2675a25`，分支 `fix/setting-sources`。

## 事实、假设与范围

2026-11-10 至 11 日，MonoCode Native 0.16.0 的 macOS disk-writes 诊断记录约 19.5 小时内累计 549.76 GB 的 file-backed dirty writes，主要堆栈经过 `PendingSave::flush`、SQLite 提交和 WAL checkpoint。这是累计写入活动；数据库最终大小、SSD 实际 NAND 写入量和进程退出原因均不能从这个数字直接推导。报告写着 `Action taken: none`。

11 月 9 日的另一次运行采样显示 UI 线程在 `Inbox::save` 等待 Store 锁，后台会话保存正在处理 JSON。当前源码仍有相同架构：

- `runtime/persistence.rs:45`：普通共享会话的保存间隔为 650 ms，boundary 绕过间隔。
- `runtime/persistence.rs:61`：保存期间持有 `Arc<Mutex<Store>>` 的锁。
- `runtime.rs:978`：先保存，再向界面发布该批更新。
- `store/shared.rs:1252`：普通会话读取当前 blocks、校验版本、merge、存储和提交。
- `store/shared/blocks.rs:436`：merge 对整段历史投影，并复制原始 blocks。
- `store/shared.rs:1117`：普通会话将完整数组序列化回 `sessions.blocks_json`。
- `inbox.rs:555`：Inbox 在 UI 回调里取得同一个 Store 锁。settings 虽已有独立存储及相同值去重，外层 Store 锁仍会阻塞它。

这些证据确认需要解决写入放大和 UI 等锁；本设计不将其称为历史闪退的确定原因。当前 Monoptah 的实际累计写入量、各项操作占比、保存延迟，仍需受控测量。

实施范围为 Native 本地拥有的普通会话。云端、远程、TUI 和既有 Mono indexed history 必须保持各自的所有权和同步规则；本轮不实现 Tauri 功能。先交付可独立验证的诊断与 UI 修正，再交付需要单独审查的数据格式变更。

## 目标

1. 普通流式保存不再随已经完成的整段历史线性重写数据。
2. 修改一个较早的工具消息，不能导致它后面所有未变化消息再次落盘。
3. 保存慢、数据库被占用时，输入、滚动和 Inbox 刷新回调能继续执行。
4. 保留消息接收、队列出队、delivery receipt、关键边界和回合结束的可靠落盘语义。
5. 明确升级、失败恢复和降级导出的行为，保留未知 JSON 字段与隐藏内容。
6. 用可重复的累计写入测量证明效果，并限制实验自身的写入。

## 固定约束

- Native only；不修改 `src/` 或 `src-tauri/` 的功能。
- 开发和验证使用 `native-dev` profile；新 worktree 首次 cargo 命令前克隆现有 target 缓存。
- 一批编辑完成后统一验证一次；修复后只重跑失败项。普通任务不反复跑完整 GPUI 测试。
- 保留 `monocode.*`、`monocode-host`、包名、crate 名、存储中的 `INTERRUPT_MESSAGE` 等既有标识。
- 不读取或输出用户消息正文、token、环境凭据作为诊断数据；fixture 全部合成。
- 不修改生产数据库做性能实验；只使用临时目录的合成库及 Native Dev 独立数据。
- 不通过关闭 journal、降低 synchronous、禁止 fsync、无限延迟 checkpoint 或无限积压内存来换取数字下降。
- 初始方案保留 650 ms 的普通保存节奏和既有强制保存边界，不用延长丢失窗口作为优化手段。
- 流式片段尚未提交时允许仍处于内存中；不能承诺异常断电后保留所有尚未提交的 token。
- 未成功提交的消息不能报告为已持久化、已接收或已完成。
- 队列出队、消息写入和接收凭证必须保留在同一个 SQLite 数据库的同一个事务内。
- 每个请求只做一次整体代码审查；迁移、数据删除和降级转换另做专门的数据安全审查。
- 本规划不授权 commit、push、合并、发布或对生产数据库执行转换。
- 每批都必须提供同一合成数据、同一事件序列、同一构建及 SQLite 配置下的修复前后对比；缺失或未完成的测量明确标记，不填 0、不推算为实测结果。
- 代码遵循周边 Rust 命名和错误处理风格；用小函数、明确的数据结构和最少抽象实现，不引入通用任务框架、插件式注册或为未来用途预建接口。
- 测试使用可移植的同步屏障和 `secondary-...` 快捷键；macOS 专属计数隔离在条件编译内，普通正确性测试可在 Linux 运行。

## 测量先行

新增内部保存统计，记录原因、提交次数、实际有变化的 rows/blocks、读入及编码字节数、锁等待、持锁、投影/编码和提交耗时。输出仅含数字与固定枚举；不含消息、路径、标题、SQL 参数和 provider 响应。

可选诊断每 60 秒输出一条汇总，复用有大小上限的日志机制。默认不逐 token、逐 SQL 或逐次保存写日志。macOS 累计进程 I/O 使用现有 `memory_log.rs` 的 `proc_pid_rusage` 模式读取 `ri_diskio_byteswritten`；其他系统无等价读数时写 `null`，不能写 0 假装没有写入。

同时保留三种不同含义的指标：编码/提交的逻辑数据量、WAL/数据库活动、操作系统报告的进程累计写入。WAL 文件大小可能循环复用，不能当累计写入量。不能为了计数安装一个意外取代默认 auto-checkpoint 的 hook，也不能在每次采样时主动 checkpoint。

基准使用 1、10、40 MiB 的合成已完成历史，混合文本、工具、Interjection、附件引用、卡片和未知字段。固定事件序列为四次 650 ms 间隔的小幅追加，随后结束；另有只更改较早工具状态、重复相同事件、5 MiB 活动工具 payload、一个很长的活动回答，以及多会话并发场景。

旧实现的大库基准每个场景只采一次，不以大量重复来统计 p95。整个基准进程累计写入预算为 512 MiB；达到预算即停止并将该场景标为未完成。低于预算并不等于完整经过所有 workload。正确性用小 fixture，耗时分位数在修复后的受控运行中测量；CI 不使用易抖动的耗时断言。

### 修复前后对比协议

- Before 是只加测量工具、尚未改保存行为的版本；After 使用同一测量工具及 fixture。为各自记录源码 SHA、未提交 diff 的 SHA、工具链、Cargo.lock SHA 和 `native-dev` profile，不以历史 MonoCode 诊断替代 Before。
- 两边固定 fixture 的 UTF-8 数据字节及 SHA、workload SHA、块/行数、事件顺序、保存参数和 SQLite page/journal/synchronous/auto-checkpoint 配置。时间戳和消息 ID 在 fixture 中固定；相同输入各自写入新的临时库。数据指纹或配置不匹配，比较器应拒绝计算改善率。
- workload 明确为四次各 1024 字节的小追加，逻辑事件时间分别为 0、650、1300、1950 ms，2600 ms 结束并执行最终保存。保存很慢时不能偷偷减少或合并事件；记录实际完成时间。其他场景同样在 manifest 中固定事件数量和内容，不调用真实 provider。
- setup/转换、热保存、最终保存及结束后一次统一 checkpoint 分段记录；工作结束并关闭数据库后读取总写入。最终 checkpoint 使用相同策略，失败或仍 BUSY 则标记未完成。记录 WAL 峰值，不能只报告清空后的大小。
- 两边相同次数的小样本报告每次原值、总量和最大值。p95 只在明确标注的至少 100 次补充小样本中报告，不把旧版四次保存和新版百次保存的 p95 作直接比较。
- 比较结果包括：累计进程写入、逻辑编码字节、提交次数、锁等待/持锁时间、保存耗时、UI 响应，以及重启后 rows/未知元数据/队列凭证的一致性。进程 I/O 是 OS 计数，不等同物理 NAND 写入；缺失为 `null`，Before 为 0 时改善率为 `null`。
- 保存原始 JSON 和生成的对比记录；预算用尽、配置不一致、任一保存失败或数据不一致时，输出“不完整/不可比较”，不得宣称达到 95%。记录两边及全部实验的累计写入成本，不能通过反复新建进程掩盖预算消耗。
- 第一批预期可证明 UI 等锁改善，transcript 仍为原 blob 格式，写入降低目标标为第二批待验收。第二批完成后使用保留的同负载基线；测量工具或配置改变时重新建立配对基线。

## 推荐架构与分批交付

### 第一批：诊断与已确认的 UI 等锁

先补齐上面的基准和失败测试。提供一个共用的设置保存组件，每个实例绑定一个固定设置 key，UI 回调只提交值，后台取得 Store 锁并在完成后通知 UI。Inbox 使用一个由 app 持有的实例；第一批不引入多 key 注册表、通用任务调度或任意数据库命令。

每个实例至多一个正在执行的保存和一个待保存的最新值。待保存的旧值可以被较新值替代；已经执行的操作有明确完成结果。仅在没有不同值正在执行或排队、且相同值已成功提交时才能直接去重，避免 A 已保存、B 正在保存时新的 A 被误丢弃。完成回调使用 generation 防止旧结果覆盖新状态；失败保留最新脏值并显示保存失败。关闭视图不应取消已经接收的保存，正常退出和重启在后台等待已接收工作结束，不在 UI 线程 join。

这一批只承诺消除已验证的 Inbox 阻塞入口，并提供可复用机制。需要审计其他同步 `locked()` 调用，尤其模型切换、卡片写入、笔记和云端操作；未迁移的调用不得被描述成已经解决。第一批不宣称已根治 transcript 写入放大。

### 第二批：普通会话的增量存储

根治方向是在同一个主 SQLite 数据库内增加普通本地会话的分块后端。原始 block JSON 保持语义格式：未知字段、隐藏 blocks、附件、卡片引用和 provider 元数据必须原样保留。不能仅存可见 Row 再丢掉其余字段。

后端由明确的存储模式和 revision 标识选择，不假装普通会话是 Mono，不复用 Mono 的同步归属、window 或 replace/snapshot 标记。普通会话采用稳定的绝对行号；UI 的分页不能改变持久化行号原点。最终表布局和 reader 切换作为独立的数据格式实现计划交付；在兼容性清单和基准完成前，不执行任何现有会话迁移。

兼容性核查已经确认以下阻碍，不能通过复用现有表名绕过：

- `store/shared/window.rs:20` 以 `mono_transcripts` marker 选择 indexed history；`:31` 将当前 Store 的原点固定在最近十个回合。`store/shared.rs:1135` 的 indexed writer 接收完整窗口后缀，不是稀疏 block 更新；长时间使用时窗口仍会增长。
- `store/shared/cloud_rows.rs:65` 拒绝 indexed histories；`cloud_sessions/move.rs:2053` 需要持久化行号。已有 turn receipts、返回本地 gate 和 `moved_at_row` 不可随 UI window 重编号。
- `store/shared/index_search.rs:26` 的 fingerprint 包括时间、blob 长度、block 数和最大 seq；仅原地改一个 block 可能不改变这些值。新模式必须将 revision 纳入失效依据，并通过同时间戳、同长度的原地编辑测试。
- `store/today_sessions.rs:220` 的旧链接回填只读 blob；`store/side_threads.rs:199` 和 `:214` 的 provider 清理及快照路径需要全历史语义。新后端需明确区分全历史访问和 UI 分页。
- `store/shared.rs:44` 的 rich-JSON revision 可以复用，但它保护当前选中的表示，不能自动检测另一个旧客户端对已废弃 blob 的修改。
- 主库 opener `store/shared.rs:234` 没有现成的未来版本写入屏障。独立 settings 库中的版本检查不能替它保护 transcript。普通 Tauri 会话仍读取/写入 blob；本轮不改 Tauri，因此必须给出清晰的旧客户端兼容边界。

原始 JSON 适配、隐藏字段保留、indexed writer 的 changed-block 比较和全历史迭代机制可以抽取复用；Mono marker、最近十回合的坐标规则以及云端拒绝逻辑不能照搬。

增量后端必须同时处理两个层次：

- 定位发生变化的 block，避免对整段已完成历史重复投影、复制和序列化。为窗口/row 到原始 block 的映射建立可失效缓存；版本冲突时重新加载或拒绝保存。
- 对一个正在增长的大 block 也进行有界的持久化，避免把全量会话写入简单变成全量大消息写入。用大工具和长回答基准决定块内分片布局；只完成按消息拆表不能通过这一项验收。

`PendingSave` 需能够表达不相邻的脏区间。某个早期工具更新和尾部 token 变化可以合并提交，但中间未变化的消息不能被复制进写任务或重复写入。旧 `write_rows` / `write_rows_with_message` 入口保留，统一委托后端，不允许调用方绕开冲突保护或事务性接收凭证。

加快 UI 发布不能改变关键事件顺序：普通文本可以先更新显示，再在原运行 worker 保存；接收凭证、visual 工具的 saved 回复、结束状态，仍在提交成功后确认。先不引入独立 transcript writer 队列，避免增加一套取消、退出和乱序语义。

### 数据转换及回退

新 reader、搜索、分叉、编辑、云端移动/导出、删除和恢复都支持新模式后，才打开写入。新格式版本高于当前程序能力时明确拒绝写入；不能把不认识的格式当空历史。

顺序为合成库、Native Dev、新建本地会话、最后按需转换现有本地会话。启动时不批量转换全部历史。每次转换先确认有可恢复的一致性备份和足够空间；该会话的完整转换与模式切换在一个事务里完成。中断、磁盘写满或提交失败保持旧格式有效，下次可重试。不得依靠 `cp` 单独复制一个正在使用 WAL 的 `.db` 来制作备份。

不能持续双写完整 `blocks_json` 维持兼容，否则会把写入放大保留下来。旧版本直接写同一份新格式数据必须被防止或明确判为不受支持；只新增一张表、任由旧程序继续写旧 blob，不算安全迁移。需要配套可验证的降级导出，将所有最新消息还原为旧格式之后再用旧版本。仅切换 Git commit 或安装旧包不构成数据回退。

转换、冲突检查和降级边界在第二批专门计划中固定后再实施；这不是可以用几行建表 SQL 跳过的工作。

## 验收门槛（目标，不是当前实测结果）

- 正确性：保存、重启、恢复后的 Row 顺序和内容一致；原始 blocks 中未知字段、隐藏 blocks、附件和卡片身份保持。
- 无变化：重复同一事件和 15 分钟会话静置不触发 transcript 数据写入。真实运行的其他功能和日志 I/O 单独统计。
- 既有历史：第二批在 40 MiB 静态历史的小追加 workload 中，相同事件序列的累计进程写入相对旧路径降低至少 95%；一次性建库/转换成本单列，不混入热保存结果，也不省略报告。
- 增长关系：增量保存的逻辑写入量不随已完成历史从 10 MiB 变为 40 MiB 而增加；报告所有新后端元数据及索引写入，不能只统计正文。
- 大消息：5 MiB 活动工具和长回答的重复小更新不能每次重写整个大消息；未达到则第二批未完成。
- 性能：受控 Mac 上新后端普通热保存目标 p95 < 50 ms；同时报告样本数和最大值。失败时保留数据并继续定位，不放宽断言。
- UI：人为占用 Store 锁 2 秒时，Inbox 刷新回调返回、输入和滚动事件仍可处理。自动化用同步屏障证明主线程能前进，不靠固定 sleep 或脆弱帧率阈值。
- 可靠性：接收事务故障后消息不会丢失/重复，队列不会提前移除；取消、关闭窗口、正常退出、重启后能恢复已提交内容。
- 并发：两个连接/窗口修改同一会话时拒绝过时写入，保留另一方内容；不同会话的保存不串数据。
- 错误：FULL、BUSY、只读、损坏/未知格式均可见且不清掉待保存状态；不报告虚假的 Ready/saved。
- checkpoint：默认策略不先调参；优化后 WAL 有界，长读事务导致的增长能够诊断。不能通过把写入推迟到基准结束以后达成目标。

## 评审与交付

第一批形成小而独立的变更，报告基线、代码覆盖范围和 UI 测试。第二批是数据格式变更，单独提交设计/实现清单和迁移安全审查；在其通过前，保持现有会话格式。每批都列明哪些目标实测通过、哪些尚未验证。历史闪退调查独立保留，不因性能改善而标记为已修复。
